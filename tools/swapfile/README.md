# Swapfile — browser-only file toolkit (PWA)

66 tools that convert, resize and edit files **entirely on the visitor's device**. No
upload, no account, no server-side processing. Served at
`https://cybernovaworks.store/tools/swapfile/`.

Each tool is its own page rather than one page with tabs, so each can rank for its
own search term ("resize video", "merge pdf", "heic to jpg"). Every page links to
the others, and the homepage hub links to all of them.

## Layout

| File | Role |
| --- | --- |
| `index.html` | Hub page — every tool as a card, grouped into 8 categories |
| `<tool>.html` | 66 generated tool pages (57 generated by `generate.mjs` + 9 hand-built) |
| `app.js` | Shell + dispatch. Owns the dropzone, file list, convert button. Holds the 9 original tools |
| `converts.js` | Conversion engine. Every tool past the original 9 lives here, including all video tools |
| `styles.css` | Tool-page design, loaded after the site theme so it can override it |
| `generate.mjs` | **The generator.** Writes all 57 generated pages + `index.html` + `home-tools.html` + `sitemap.xml` |
| `home-tools.html` | Build intermediate — a copy-paste block for the site homepage's tool chips. Not part of the app, safe to ignore |
| `service-worker.js` | Offline caching (app shell only — see below) |
| `manifest.json`, `icon.svg` | PWA install metadata |

### How a tool is wired

1. `generate.mjs` has an `add({...})` entry per tool: `key`, category, icon, colour,
   file name, SEO copy, how-it-works steps, and FAQ.
2. `converts.js` has the matching `convert` function and an `EXTRA_TOOLS` entry
   (`accept`, `dropLabel`, `dropHint`, `convert`).
3. The page's `<body data-tool="key">` tells `app.js` which tool to run.

`app.js` merges `window.EXTRA_TOOLS` into its own `TOOLS` map, so `converts.js` must
stay loaded **before** `app.js` (the script order at the bottom of every page).

> **Both files are classic scripts, so they share one global lexical scope.** A
> top-level `const` / `let` / `class` declared in *both* files is a **parse-time
> `SyntaxError`**, and it kills the *entire* second script — not just the duplicate
> line. Because the merge and the dropzone wiring both live in `app.js`, one
> colliding name silently turns every generated tool into a dead UI with no visible
> error. This happened for real: both files had `const PDF_WORKER_SRC`, so all 57
> generated tools were dead while `node --check` passed on each file in isolation.
>
> Rules: keep shared/internal names unique across the two files, and prefix anything
> private to `converts.js` with `_` (as with `_pdfWorkerSrc`, `_loadedLibs`,
> `_rsSource`). If you ever need a name in both, put it on `window` explicitly.

**Check this before deploying.** `node --check` cannot detect it; the two files have
to be loaded into one shared context:

```
node test-load.js .        # asserts both load together, and that every page's
                           # data-tool resolves to a tool with a callable convert()
```

### Adding a tool

Add the `add({...})` entry in `generate.mjs`, add the function and the `EXTRA_TOOLS`
entry in `converts.js`, then:

```
node generate.mjs
```

Never hand-edit the generated `.html` files — they are overwritten. Only `styles.css`
and the generator's own template logic are edited by hand.

### Tools with settings

Tools that need options (resize, trim, rotate, frames, watermark) add a `panelExtra`
block, which the generator injects between the file list and the convert button. It
uses the existing `.tool-opts` / `.preset-btn` / `.opt-field` / `.opt-check` CSS.

`converts.js` wires it through `_initOptsPanel(id, onChange, onPreset)`, which handles
preset-button selection and live note updates. `_initToolPanels()` calls it for
whichever panel the current page has. A tool may also expose `onFiles(files)` in
`EXTRA_TOOLS`; `app.js` calls it when the visitor picks a file, which is how the tools
read the source resolution and duration.

## Video tools

All video work runs through **FFmpeg.wasm** (`@ffmpeg/ffmpeg@0.12.10` + `@ffmpeg/core@0.12.6`,
loaded lazily from unpkg — about 30 MB, one time, then cached). `runFfmpegCommand()` in
`converts.js` is the shared wrapper; it handles engine loading, writing the input,
running, cleanup, MIME typing and the download.

Gotchas worth knowing before you touch the filter strings:

- **Commas inside `min()` must be escaped** (`min(1280\,iw)`). ffmpeg reads an
  unescaped comma as a filter-chain separator and the whole command fails with
  "Error opening output files". Values wrapped in single quotes are safe instead.
- **Every output dimension must be even.** `yuv420p` refuses odd sizes, and FFmpeg's
  own `testsrc` will not even generate them. The resize tool rounds via `_rsEven()`;
  percentage presets use `trunc(iw*0.5/2)*2` for the same reason.
- `oh` must not reference `ow` — it evaluates before the output size exists and comes
  out `nan`. Both derive from `iw`/`ih`.
- Browsers cannot always read a container (MKV, some HEVC), so anything that needs the
  source size degrades to a fixed-size fallback instead of failing.

## Offline / PWA

`service-worker.js` deliberately precaches **only the app shell** (`index.html`,
`styles.css`, `app.js`, `converts.js`, `manifest.json`, `icon.svg`, `../../script.js`).
Tool pages are cached by the fetch handler the first time they are opened, so a tool
works offline once visited.

Precaching all 66 pages was rejected on purpose: it is about 1 MB, and `cache.addAll()`
is atomic, so a single bad URL would fail the whole install and leave the app with no
offline support at all. The shell list is identical for every tool, so it never needs
updating when tools are added.

**Same-origin requests are network-first, with the cache as the offline fallback.**
This is deliberate, and it was learned the hard way. The strategy used to be
cache-first, which meant a deployed fix was invisible to every returning visitor
until someone remembered to bump `CACHE_NAME` by hand — so when a broken `app.js`
got cached that way, the site stayed broken even after the fix had shipped.
Network-first means a deploy is visible on the next load, and going offline still
works off the cache. Nothing needs a manual version bump any more.

CDN assets (unpkg, cdnjs) are not intercepted at all: they are versioned and
immutable, so ordinary HTTP caching is already correct for them.

One caveat that remains: right after a push, the *first* reload can still be
served by the outgoing service worker while the new one installs in the
background. A second reload is always enough, and clearing site data by hand
should never be necessary.

## Deploying

`website/` is a standalone repo. **The live site is served from the `gh-pages` branch**,
so pushing to `master` alone changes nothing:

```
node generate.mjs
git add -A && git commit
git push origin master
git checkout gh-pages && git merge --no-edit master && git push origin gh-pages
git checkout master
```

Canonical URLs and JSON-LD are hard-coded to `https://cybernovaworks.store/tools/swapfile/`.
Deploying elsewhere means changing `BASE` in `generate.mjs` and regenerating.

GitHub Pages takes roughly one to two minutes to publish, so verify over HTTP rather
than assuming the push went live.

The site-wide `sitemap.xml` and the `home` page's tool chips are **not** written by the
generator — they are hand-maintained, and adding a tool means adding an entry to each.
The per-tool `sitemap.xml` here *is* generated.

## Known limits — be upfront with users

- **Everything video** re-encodes, so it is slower than a remux and briefly needs a lot
  of memory. Very long clips may fail on low-memory phones.
- **FFmpeg.wasm is single-threaded**, so a 10-minute 4K clip takes real time. There is
  no progress bar; the button shows a spinner.
- **Word → PDF** approximates layout via HTML rendering, not pixel-perfect.
- **PDF → Word** extracts text only — no images, tables or exact layout.
- **Compress PDF** rasterises pages, so the output is no longer selectable text. Best for
  scanned or image-heavy PDFs.
- **Watermark** re-encodes the whole clip, and a JPG logo shows as a solid rectangle —
  use a transparent PNG.
- **HEIC → JPG** depends on `heic2any`; unusual HEIC variants from some Android phones
  may fail to decode.
- **First video use is slow** (~30 MB engine download). Tools that only need the source
  size read it with a plain `<video>` element, so the panel fills in immediately.
